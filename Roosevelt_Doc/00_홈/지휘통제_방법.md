# 멀티 세션 지휘통제 방법

## 구조
- 지휘 세션 1개가 사용자 지시를 받아 쪼개고, 워커 세션(같은 폴더의 다른 Claude)에 SendMessage로 분배한다. 워커는 `ListAgents`로 찾는다.
- 워커는 끝나면 지휘 세션에 보고한다(바꾼 파일, 확인 방법과 결과, 남은 일). 지휘 세션이 검토·통합·커밋한다.

## 지시문에 꼭 넣을 것
1. 범위: 건드릴 파일·폴더 목록(겹치지 않게)
2. API 계약: 클래스·메서드·필드 이름. 서로 의존하면 한쪽이 먼저 "컴파일되는 API 파일"을 만들고 상대에게 알린다
3. 확인 기준: 컴파일 에러 0개, 필요한 테스트
4. 금지: 커밋·push, `.meta` 직접 작성, 빌드 요청 파일 생성, CLAUDE.md·설정 변경

## 규칙
- 커밋·push는 지휘 세션만, 사용자 확인 뒤 영역별로. 메시지는 UTF-8 파일 + `git commit -F`(PowerShell 5.1 스크립트 안의 한글은 깨짐)
- Git LFS 안 씀(GitHub 예산 초과). mp3는 `.gitignore`
- Unity 에디터는 하나: 배치모드 금지. 새 코드는 사용자가 Unity를 클릭해야 컴파일된다
- 씬 빌드: `Temp/LabSceneBuilder.request`에 배치 이름을 줄마다 쓴다(비우면 전부 빌드, Forest_Test 덮어씀). 새 빌더 코드가 컴파일된 뒤에만 요청(스크래치패드의 `build-when-compiled.ps1` 방식)
- 컴파일 확인은 에디터 없이 Roslyn(`dotnet …\Roslyn\bincore\csc.dll`) + csproj 참조로. asmdef(Core)를 먼저 컴파일해 참조
- Domain Reload 꺼짐: 정적 상태는 `SubsystemRegistration`에서 초기화
- Blender MCP는 한 번에 한 세션
- Codex는 쓰지 않는다(사용자 결정)

### 이 단계에서 배운 것
- 워커 보고를 그대로 믿지 마라. 2d가 "FAILED ASSEMBLIES: 0"으로 두 번 보고했지만 둘 다 실제로는 틀렸다(루프 설정이 no-op, CS0201). `compile-check.ps1`은 중간 출력이 `Select-Object -Last 1`에 삼켜져 요약만 남으므로, **`compile-out\*.rsp`로 csc를 다시 돌려 에러 줄을 직접 봐야** 한다
- 리깅은 파이프라인 전제를 깬다. 정적 → 스킨 메시로 바뀌면 (1) `MeshRenderer`로 좁혀 잡는 코드가 통째로 안 돈다(`SkinnedMeshRenderer`는 형제 클래스라 머티리얼·바운즈가 날아가 흰 모델 + 0 크기 콜라이더), (2) `Animator`가 FBX에 딸려 와서 `AddComponent`가 null을 반환한다. `GetComponent ?? AddComponent`로 쓰되 **대입 없는 자리에서는 `??`가 문이 될 수 없다**(CS0201)
- `ModelImporter.clipAnimations`는 접근할 때마다 복사본이다. 배열째 다시 대입해야 남고, 새 FBX는 이쪽이 비어 있어 기본 클립은 `defaultClipAnimations`에 있다. 클립 설정은 `OnPreprocessAnimation`에서
- 소비되지 않은 `SetTrigger`는 남는다. Any State 전환이 있으면 강제 `Play("Idle")` 직후 다음 프레임에 다시 발동하므로 `ResetTrigger`가 필요하다
- **컴파일 경합**: 워커가 새 파일을 저장하는 사이에 Unity가 컴파일을 시작하면, 그 파일을 참조하는 쪽만 읽혀 CS0246으로 깨진다. 이후 `AssetDatabase.Refresh()`는 "변경 없음"이라 재시도하지 않아 **낡은 어셈블리가 계속 로드된 채로 빌드가 성공한다**(빌드 결과만 보면 눈치채기 어렵다). `Library/ScriptAssemblies/Assembly-CSharp.dll`의 타임스탬프를 소스와 비교해 확인하고, 소스를 touch한 뒤 사용자에게 Unity 창을 누르게 해야 풀린다

- **흔들림 감쇠 `BoatBuoyancy.tiltScale`(기본 0.35).** 사용자가 "너무 심하게 흔들린다"고 했고 실측이 맞았다 — 실제 수면 기울기는 수직 기준 **최대 12.66°(진폭 25.3°)**, 주기 3~10초. 0.35를 걸면 최대 4.43°(진폭 8.9°)가 된다. 상하(heave, 범위 1.27m)는 **일부러 안 줄인다** — 그게 배를 수면 위에 얹어두는 값이다. 배가 물보다 덜 기울면 뱃머리·고물이 파도를 뚫을 위험이 생기는데, 오프라인 스윕으로 최악 여유가 `+0.292m → +0.140m`로 줄지만 **여전히 양수**라 침수는 안 난다. 플레이 중 밖에서 배를 볼 일이 없고 앉은 눈높이에선 선체가 흘수선을 가려서 치팅이 안 보인다

### 이 단계에서 배운 것
- **타일링의 주범은 파도가 아니라 꼭대기 하이라이트였다.** 사인파 합의 피크는 완벽한 격자 위에 생기는데, 크레스트 틴트가 그 격자점마다 밝은 도장을 찍어 안 보였을 규칙성을 드러냈다. 뺐더니 해결. 파장을 서로 약분 안 되게(7.3/4.7/11.9/3.1), 방향을 0°/37°/101°/149°로 잡은 것도 함께
- 반복 검증은 **위에서 내려다보는 직교 캡처**로 한다. 비스듬한 시점은 "괜찮은데?" 하고 넘어가기 쉽다
- 셰이더의 `_Time.y`는 `Time.time`이 아니라 **`Time.timeSinceLevelLoad`**. C#에서 같은 파도 수식을 평가할 때 틀리면 배가 서서히 어긋난다
- 에디터에서 Play 없이 `Camera.Render()`만 연달아 불러도 `_Time`이 흐른다는 보장이 없다. `_TimeOffset` 프로퍼티로 시각을 강제해 캡처한다(`CreatureBuilder`가 `StalkWalker.Tick()`을 직접 부르는 것과 같은 이유)
- **"이동만 잠금, 시점 자유"는 이미 있던 기능이었다.** `FirstPersonController.Update`에서 `Look()`은 `InputLock`만, `Move()`는 `posed`만 본다. `SetPosed(true)`를 `InputLock.Acquire()` 없이 부르면 된다. 의자·침대가 항상 둘 다 잡아서 쓰인 적이 없었을 뿐. **지휘실이 "없다"고 단정했으나 워커가 코드를 읽고 찾아냈다 — 없다고 말하기 전에 읽어라**
- 배가 물에 뜨는지 판정할 때 **진폭과 건현을 나란히 비교하는 건 범주 오류다.** 배가 수면을 따라가면 건현은 진폭과 무관하게 일정하다. 실제 변수는 **선체 길이 대 파장 비**(2.42/3.1 = 78%) — 배 밑 수면이 평면으로 근사되지 않는 것이 원인. 진폭을 줄이면 수평선 실루엣만 잃고 원인은 남는다
- `delayCall`로 만드는 설정 에셋과 `EditorApplication.update`로 폴링하는 빌더는 **실행 순서가 보장되지 않는다.** 빌더가 값을 읽기 전에 에셋 존재를 동기적으로 보장해야 한다(`EnsureExists()`)
- 런타임 한계(알고 남겨둠): Play 도중 `OceanSettings`를 바꾸면 배(C#)는 즉시 따라가지만 머티리얼은 안 따라간다. 폭풍 연출처럼 런타임에 파도를 바꿀 계획이 생기면 밀어넣는 컴포넌트가 하나 더 필요하다
- **플레이어가 실제로 보는 시점을 재현하지 않으면 안 보이는 버그가 있다.** 배 침수가 그랬다 — 월드 고정 카메라 캡처 세 종류가 전부 "흘수선 완벽"이라고 말하는 동안, 앉은 눈에 매단 카메라 한 장이 배 안이 물로 차 있는 걸 즉시 드러냈다. 캐릭터가 고정된 시점을 갖는 장면에는 그 시점 캡처를 반드시 넣는다
- **물 격자에는 배 구멍이 없다.** 흘수(선체 바닥이 수면 아래)는 설계상 정상인데, 연속 격자가 선체를 통과하고 물이 불투명이라 안에서 보면 침수로 보인다. 해법은 (a) 안쪽 바닥판을 흘수선 위로 — 실제 스키프 구조이고 셰이더 작업 없음, (b) 스텐실 마스크, (c) 배가 XZ로 안 움직이면 물 프래그먼트에서 타원 `discard`. **`discard`는 물을 지울 뿐 나무를 보이게 하지 않으므로 (a)는 어차피 필요하다** → (a)로 해결됨
- **렌더 픽셀을 세는 검증은 거짓 통과할 수 있다.** 70이 물을 마젠타로 칠하고 픽셀 수를 셌더니 0이 나왔는데, 통과가 아니라 테스트 고장이었다 — 톤매핑이 emission (1,0,1)을 분홍(#d98fd0)으로 바꿔 임계값에 안 걸렸다. 렌더를 눈으로 열어보고서야 발견. 리뷰 스크립트는 view transform을 Standard로 고정할 것. 그리고 **테스트에 이빨이 있는지 음성 대조군으로 확인해라**(70은 바닥판을 일부러 물 아래로 내려 2836/6384가 실패하는 걸 확인했다)
- **포말(whitecap)을 다시 넣었다. 그런데 격자는 "높으면 흰색"이라는 규칙으로는 못 없앤다.** 사용자 요청으로 물마루 흰 거품을 복원하면서 다섯 번 시도했다: (1) 임계값에 노이즈, (2) 노이즈가 올리기만 하게(골에 흰색 번지는 것 방지 — 이건 유지할 가치가 있다), (3) 샘플 위치를 노이즈로 미는 domain warp, (4) 가장자리를 잘게 부수는 erosion, (5) erosion을 서브미터로. **모양은 매번 나아졌지만 격자는 다섯 번 다 남았다.** 이유가 구조적이다 — 사인파 합의 국소 최대는 격자 위에만 있으므로, **포말이 생길 수 있는 후보 위치 자체가 격자다.** 솎아내면 살아남은 것들이 격자를 그리고, 밀어내면 격자가 통째로 조금 움직일 뿐이다. 진짜로 없애려면 파도 장 자체를 비주기적으로 만들어야 한다(파도 개수를 6~8개로 늘리거나, 높이에 노이즈 항을 더하되 셰이더와 C# 양쪽에 똑같이 — 후자는 부력에 영향이 가므로 재검증 필요)
- **단, 격자는 위에서 60m 직교로 내려다봐야 보인다.** 앉은 눈높이(0.9m) 정면에서는 안 보인다. 직교 캡처는 일부러 가혹하게 보는 검사이고, 게임에 그 시점은 없다. 이걸 고칠지 말지는 비용 대비 판단이고 사용자 몫으로 남겼다
- **머티리얼과 ScriptableObject는 "이미 저장된 값"으로 셰이더/C# 기본값을 덮는다.** 포말 기본값을 셰이더에서 바꿨는데 그림이 그대로였다. `.mat`이 첫 기본값을 이미 직렬화해뒀기 때문이다. 그래서 포말도 파도처럼 `OceanSettings`에 넣고 빌더가 밀어넣게 했다. **검증은 렌더를 보지 말고 `.mat`을 grep해서 값이 실제로 들어갔는지 확인해라** — 이것 때문에 어셈블리 경합과 구분이 안 돼 한 번 더 헛돌았다
- **"플레이어 시점 재현"은 위치만으로 부족하다 — 카메라 설정도 재현해야 한다.** 앉은 정면 캡처를 넣고도 하늘 검정 버그를 못 잡았다. 빌더가 만든 카메라에 `clearFlags = Skybox`를 직접 박아뒀는데, **`PF_Player`의 카메라는 `SolidColor` 검정**이기 때문(연구소가 의도적으로 쓰는 값. `LabSceneBuilder.SetupEnvironment`는 야외일 때 씬의 모든 카메라를 `Skybox`로 바꾸는데 `OceanTestBuilder`엔 그 처리가 없었다). 지금은 (a) 야외 씬이면 모든 카메라를 `Skybox`로 바꾸고 (b) 앉은 캡처 카메라가 `CopyFrom(플레이어 카메라)`로 시작한다. **프리팹 기본값은 건드리지 않았다** — 연구소가 그 검정에 의존한다
- **컴파일 경합은 지휘실에도 그대로 온다.** 빌더 스크립트를 고치고 곧장 request 파일을 넣었더니 빌더가 **옛 어셈블리로 돌아 새 캡처가 안 나왔다**(빌드 21:53:32 / dll 21:54:03). 로그에는 성공만 찍힌다. 소스와 `Library/ScriptAssemblies/Assembly-CSharp-Editor.dll` 타임스탬프를 비교하고, dll이 더 새로우면 request를 한 번 더 넣으면 풀린다
- 숫자 가정은 실측으로 바꿔라. b1이 건현을 전 구간 0.270으로 가정해 "최악은 고물"이라는 결론을 냈는데, 70의 실측표(뱃머리 0.336/고물 0.292/중앙 0.270)를 넣으니 최악이 중앙으로 옮겨갔다. 선미 로커가 바닥을 들어올려 고물이 중앙보다 높은 배였다

## 노 젓기 (2026-09-14 새벽, 진행 중)
- 사용자 설계: 노 2개. **왼쪽 노 = 왼쪽 회전, 오른쪽 노 = 오른쪽 회전, 노 중간 = 전진.** 시선 상호작용 세 개로 가른다
- **방향 전환이다.** 커밋 `de35403`과 `BoatBuoyancy` 주석이 "배는 제자리, 물이 흐른다 / 망망대해의 공포는 나아갈 수 없음에서 온다"로 박혀 있었다. 사용자 승인 받고 뒤집었다
- **지휘실이 처음에 "배를 실제로 움직이는 건 제일 비싸다"고 했는데 틀렸다.** 근거 셋을 실제로 검증해보니 전부 무너졌다: ① `SetPosed(true)`가 `body.enabled = false`라 **탑승 중엔 CharacterController가 꺼져 있다** — 이동 플랫폼 문제 자체가 없음 ② float32 정밀도는 10km에서 0.6mm, 초당 1.5m로 1시간 50분 거리라 규모가 안 됨 ③ 셰이더가 파도를 월드 좌표로 샘플링하므로 물 메시를 칸(2m) 배수로 스냅해 따라가게 하면 끝, 다섯 줄. **옛 설계 근거를 지금 코드와 실제 규모에 대보지 않고 그대로 읊은 것**이 원인이다. 사용자가 "심각한 수준이야?"라고 되물어서 잡았다
- 오히려 "파도 장 오프셋만 움직이기"가 더 비싸다 — 오프셋을 셰이더와 C# 양쪽에 넣어야 해서 조용한 어긋남 위험이 생기고, 바다에 다른 오브젝트를 놓으면 그것만 배에 붙어 다닌다
- **실측 계약(지휘실 고정):** 노받이 피벗 배 로컬 `(±0.447, 0.350, +0.250)`, 좌판 `(0, 0.150, -0.050)`이라 노받이는 앉은 자리 30cm 앞. 노 FBX는 **원점이 이미 노받이 피벗**(`make_dream_boat.py` 주석)이라 오프셋 없이 놓고 자기 원점으로 돌리면 젓기가 된다. 블렌더에서 날이 +X라 변환 후 Unity 로컬 -X를 향하므로, `x=+0.447` 쪽 노만 Y 180° 회전
